# 07 · 자주 발생하는 문제와 경험

이 과정에서 실제로 겪은 문제들을 증상별로 빠르게 찾아볼 수 있습니다.

## 환경 관련

| 증상 | 원인과 해결 방법 |
| --- | --- |
| `uv sync`가 `failed to persist temporary file ... os error 17（跨盘）`을 보고 | 이 머신의 uv 캐시 디렉터리 크로스 드라이브 Windows 특례입니다. 모든 uv 명령 앞에 `export UV_CACHE_DIR='C:\Users\admin\AppData\Local\Temp\uv-cache'`를 추가하세요 |
| 콘솔에 `libtorchcodec_core*.dll` 로드 실패가 수십 줄 출력 | 노이즈 경고: torchcodec 로드 실패 후 자동으로 **pyav**로 폴백합니다. 실측(smoke [5]) 결과 pyav는 **비디오 데이터셋 인코딩/디코딩 모두 정상**이며, 상태 데이터셋과 비디오 데이터셋 모두 영향을 받지 않습니다 |
| `python` 실행 시 Microsoft Store가 열림 | uv가 관리하는 Python을 사용하세요. Store 버전은 쓰지 마세요 |

## 텔레오퍼레이션 관련

| 증상 | 원인과 해결 방법 |
| --- | --- |
| 키보드 제어가 "매우 느림" | `--teleop.rate` 기본값 60 단위/초는 보수적입니다. **150**으로 올리면 감각이 정상이 됩니다(전체 스트로크 약 1.3s) |
| 시작 로그에 `clamped to be safe` WARNING이 반복 출력 | 속도 제한기가 따라잡는 과정의 정상 출력이며, 목표에 도달하면 멈춥니다 |
| 리더 암을 중앙에 두었는데 시뮬레이션 암이 몇 도 어긋남 | 캘리브레이션 범위 비대칭으로 인한 고정 편향입니다. `so101_leader_trim`으로 자동 미세 조정하세요([05](05-leader-digital-twin.md)) |
| 연결 순간 암이 갑자기 움직임 | 설계된 동작입니다. 실기는 토크가 걸린 뒤 중간점/리더 암 자세를 향해 이동하므로 손 주변에 공간을 남겨 두세요 |
| Ctrl-C 종료 후 암이 힘없이 처짐 | 정상입니다. 연결 해제 시 토크가 꺼지므로 손으로 받쳐 주세요 |
| 텔레오퍼레이션/녹화 중 타이핑하면 암이 구동됨 | 키보드 리스닝이 **전역이며 키를 삼키지 않기** 때문입니다. 어느 창에서든 매핑 키(한글/병음 자모 포함)를 누르면 키 큐에 들어갑니다. 키보드 모드 텔레오퍼레이션/녹화 중에는 타이핑하지 마세요. 리더 암 모드에는 이 문제가 없습니다 |

## 녹화 관련

| 증상 | 원인과 해결 방법 |
| --- | --- |
| `q`로 종료한 뒤 세션 중에 누른 글자가 "한꺼번에 명령줄에 쏟아짐" | Windows 콘솔 입력 버퍼의 적체분이 다시 표시되는 현상입니다. 런처에 `drain_pending_keys()` 정리가 내장되어 있습니다(구 버전 세션에서만 나타나는 현상) |
| 특정 에피소드의 action span이 전부 0 | 빈 녹화(사람이 움직이지 않음)입니다. 녹화 전에 먼저 한 번 움직이거나, 나중에 해당 에피소드를 삭제하세요 |
| 에피소드 시작 1초 구간의 오차가 큼 | 수렴 구간입니다. 녹화 시작 순간 팔로워 암은 아직 초기 자세에 있고 리더 암은 다른 곳에 멈춰 있기 때문입니다. 리더 암을 미리 중간 위치 근처에 두면 피할 수 있습니다 |
| `--dataset.root`를 상위 디렉터리로 설정하자 데이터셋이 "사라짐" | **root가 곧 데이터셋 디렉터리 자체**입니다. 녹화 세션마다 새 root로 바꾸세요 |
| `Esc`와 `q`의 차이 | `q`는 녹화만 중지하고, `Esc`는 키보드 텔레오퍼레이션도 끊습니다. 둘 다 깔끔하게 마무리되지만(수정 완료) `q`를 습관처럼 사용하세요 |
| 저장 시 `ValueError: You must add one or several frames...`와 함께 프로세스가 오류로 종료 | 에피소드 **간격**에 `→`/`n`을 추가로 눌렀기 때문입니다(가장 흔한 경우: 저장+2경로 비디오 인코딩 정지가 수십 초 이어져 콘솔이 멈춘 것처럼 보이자 참지 못하고 여러 번 연타). 플래그가 다음 에피소드 시작까지 남아 소비되어 → **0 프레임 빈 에피소드**가 되고, 업스트림이 빈 에피소드를 저장할 때 크래시합니다(lerobot의 알려진 경계 사례). **이미 저장된 에피소드는 영향받지 않으며 데이터는 온전합니다**. 세션을 다시 열어 이어서 녹화하면 됩니다. **보호 조치 추가**(2026-10-16): `record.py`가 각 에피소드 시작 시 간격 동안 남은 `→`/`←` 플래그를 지웁니다(녹화 중 키 입력은 정상 작동). 저장 전에 `saving the episode + encoding videos now...` 안내를 출력합니다. 회귀 테스트 `smoke_test.py` [7] |
| 녹화 시작 순간 `KeyError: 'wrist'`(이미지 데이터셋) | 카메라 첫 프레임이 아직 렌더링되기 전에 녹화 루프가 관측을 읽었기 때문입니다. **수정 완료**(2026-10-16): 로봇 플러그인의 `connect()`가 이제 첫 프레임이 준비될 때까지 기다린 후 반환합니다 |
| 비디오가 포함된 스크립트가 `BrokenProcessPool` / `Invalid argument: '<stdin>'` 보고 | 비디오 인코딩이 **멀티프로세스 풀**을 사용하며, 자식 프로세스가 파일 경로로 진입 모듈을 다시 임포트해야 하기 때문입니다. 녹화 스크립트를 `python - <<EOF`(stdin)로 실행하면 크래시합니다. 스크립트를 실제 `.py` 파일로 저장한 후 실행하면 됩니다(실제 진입점 `record.py`는 영향 없음) |
| 에피소드 저장 시 `SvtMalloc[fatal]: allocate memory failed ... av.error.MemoryError: [Errno 12] ... 'avcodec_open2(libsvtav1)'`와 함께 세션 전체 종료 | 업스트림 기본 인코더 **libsvtav1**이 듀얼 카메라(wrist+top) 두 경로 인코딩을 동시에 열 때 한 번에 큰 메모리 블록 할당에 실패한 것입니다(시뮬레이션+미리보기 창 점유 상황에서 더 쉽게 발생; 2026-10-16 실측으로 겪음). **수정 완료**: `record.py`가 기본으로 `--dataset.rgb_encoder.vcodec=h264`를 주입합니다(2경로 h264 동시 인코딩 실측 통과; vcodec을 명시하면 덮어쓸 수 있음). 이미 저장된 에피소드는 무손실이며, 크래시 시 데이터셋 디렉터리에 `tmp*/`와 고아 parquet이 남을 수 있습니다(run2 방식대로 정리) |
| 녹화 중 화면이 끊김(특히 `→`를 누른 뒤). 하지만 조작에는 실제 지연 없음 | 끊기는 것은 **저장/인코딩 구간**입니다. 인코딩 프로세스가 기본적으로 CPU를 전부 사용하고(2경로 비디오 동시), 동시에 시뮬레이션 스레드가 5개 화면을 렌더링하기 때문입니다(내장 GPU에서 더 두드러짐). 제어 루프 자체는 영향을 받지 않습니다. cadence 수치를 기준으로 보세요(실측 전 구간 29.97Hz, tick 예산 초과 0건). **완화 완료**(2026-10-16): `record.py` 기본 `--dataset.encoder_threads=2`(경로당 인코딩 2스레드 제한); 카메라 미리보기 창 갱신을 15Hz로 하향(`--robot.preview_fps`). 에피소드가 짧을수록 저장 구간 비중이 커져 더 끊기는 느낌이 납니다. 정지를 완전히 없애려면 `--dataset.streaming_encoding=true`(녹화와 동시에 인코딩, 업스트림 권장, 실측 대기)를 사용할 수 있습니다 |
| 에피소드 저장 시 인코더가 **메모리 할당 실패**를 보고하고 세션 전체 종료(svtav1의 `SvtMalloc`, x264의 `malloc ... failed`, `avcodec_open2` 오류가 모두 이 부류) | 이 머신의 시스템 커밋 메모리(commit)가 장기간 한계에 근접해 있었습니다(2026-10-16 실측 **105.9GB / 119.7GB**, 연속 가동 29일). 저장할 때마다 인코딩 프로세스 2개를 새로 띄우고(각각 torch/av를 로드해 commit 스파이크가 큼), 절벽 끝에서 동시에 시작하면 실패합니다. **완화 완료**: `record.py`가 이제 인코딩에 **실패 시 자동 재시도 1회**를 추가했고(일시적 실패로 에피소드를 잃지 않음), 저장 중 로그 폭주도 음소거했습니다(`av.logging.set_libav_level` + HF 진행 표시줄). **근본 해결 = 머신 재부팅**(장시간 가동으로 누적된 commit / 커널 누수 정리; 사용자 공간 프로세스는 27GB만 차지하고 나머지는 커널/드라이버 계층이라 죽일 수 없음). 자가 점검: `Get-Counter '\Memory\Committed Bytes'` vs `'\Memory\Commit Limit'` |

## 설계 설명(왜 이렇게 했는가)

- **MuJoCo는 메시 정점 데이터를 재작성합니다**: `<mesh>`를 로드하면 `mjModel.mesh_vert`에는 **메시 자체 좌표계**의
  정점이 저장되며(원점이 정점 무게중심으로 재설정되고 축이 재배열됨), 더 이상 파일의 원본 좌표가 아닙니다. 이를 그대로 사용해 바운딩 박스를 계산하거나 CAD 치수를 맞추면
  잘못된 결과가 나옵니다(렌더링 표시에는 영향 없음). CAD 실제 형상을 얻으려면 원본 파일을 파싱해야 합니다(`preview_mount.py` /
  `step_to_stl.py`의 방식). 한 번 겪은 사례: 브래킷 실제 치수 54.3 × 35.0 × 75.0 mm.
- **MuJoCo 카메라의 뷰 방향은 좌표계의 −Z입니다**: `<camera>` 요소는 자신의 +Z(렌즈 돌출 방향)를 바라보지 않습니다. 첫 버전의
  카메라 모듈은 렌즈를 +Z에 두고 요소 방향을 identity로 했기 때문에, 화면이 실제로는 PCB 뒷면에서 "거꾸로" 비춰졌습니다. **렌즈 방향과 화면 방향이
  정확히 반대**였던 것입니다(파라미터 조정 시 "회전 방향과 화면이 맞지 않는" 근본 원인; 2026-10-16에 빨강/파랑 판 대조 렌더링 테스트로 규명).
  수정: 카메라 요소를 Y축 기준 180° 회전(`view.quat = RPY(0,180,0)`, preview_mount / adjust_camera / 로봇 플러그인
  세 곳 통일); `adjust_camera.py`에 "sim_cam live view" 실시간 화면 창 추가, 렌즈 조정 시 보이는 그대로 확인 가능.
- **공식 튜토리얼 MJCF의 그리퍼는 "새부리식" 점 접촉 그리퍼입니다**: 두 톱니 끝이 ~2.3 mm 점 접촉으로 닫히며, 사용 가능한 파지 면이 거의 없습니다.
  체계적 물리 실험(2026-10-16, 수백 회) 결론: 블록을 톱니 입구 근처 어디에 두어도 ~100°의 닫힘 스윕에서
  밀려나거나 쐐기처럼 튕겨 나가 집을 수 없습니다(16–34 mm 블록 모두 그러함; 기계적 스트로크와 토크 자체는 정상). **주의: "충돌 조각을 덧대는" 방식으로
  고치지 마세요** — 두 그리퍼에 톱니판을 덧대는 방법을 시도한 적이 있는데(파지가 크게 개선됨), 그것은 **실기에 존재하지 않는 형상**이라 학습된 정책이
  여기에 의존해 sim2real 왜곡을 일으키므로 철회했습니다. 올바른 수정 방법은 **실기의 그리퍼 형상으로 공식 모델의 그리퍼를 교체하는 것**입니다(예:
  mujoco_menagerie의 SO-ARM101 또는 자체 CAD 재구성). 물리 파라미터는 실기와 일치하게 유지해야 합니다.
- **공식 기본 접촉 파라미터가 너무 "무른" 탓에 물리적 관통이 발생합니다**: `solref` 시간 상수 기본값이 20 ms라서 빠르거나 얇은 접촉
  (블록이 얇은 그리퍼 면에 떨어지거나 닫힘 스윕)에서 "힘이 생기기도 전에" 서로 통과해 버립니다. 증상은 "블록이 그리퍼 면을 뚫고 떨어지는" 것입니다.
  수정(2026-10-16): 접촉 파라미터 경화 — `harden_mesh_contacts`가 컴파일 후 모든 메시 충돌체의 `solref`를
  menagerie 톱니 면과 동일하게(0.01 s) 경화하며, 블록 접촉도 동일하게 처리합니다. 순수 물리 충실도 수정이며 형상은 전혀 추가하지 않습니다.
- **시뮬레이션 로봇이 mujoco_menagerie의 SO-ARM100 모델로 이전되었습니다**(2026-10-16): 원래 튜토리얼 zip의 MJCF는
  운동학 데모용이라 그리퍼가 집을 수 없었고, menagerie 모델은 실기 CAD를 반영해 그리퍼에 전용 충돌 톱니 면과 경화된 접촉 파라미터가 있으며,
  네 가지 톱니 위치(얕음→깊음) 모두 실측에서 34mm 블록을 걸림+파지+들기 가능했습니다. 이전 요점: 모델은
  `assets/menagerie_so_arm100/`에 vendored(Apache-2.0, LICENSE 포함); 관절 매핑과 단위 부호는 `MODEL_JOINT` 참조
  (관절별로 구 모델과 월드 좌표 운동을 대조 측정; wrist_roll 부호는 실기 텔레오퍼레이션으로 재확인 대기); 모델 Base를 Z축 기준 +90° 회전해
  작업 정면이 +x를 향하게 함; 브래킷은 Fixed_Jaw(6번 서보) 측면에 재장착(먼저 파싱 검색으로 위치 파악, 2026-10-16 사용자가 실기

- **왜 conda 대신 uv 프로젝트 환경을 쓰는가**: `.venv`는 프로젝트와 같은 디렉터리에 있고, `uv.lock`으로 버전이 잠기며, 디렉터리를 지우면 바로 회수되고,
  머신의 conda 환경과 완전히 격리됩니다. `uv run`은 활성화된 conda에 절대 설치하지 않습니다. 이 머신의 `lerobot` conda 환경은
  **다른 저장소 사본**(`lerobot-main`)을 가리키며, 둘은 서로 간섭하지 않습니다.
- **왜 플러그인을 모두 `examples/so101_mujoco/`에 두는가**: 공식 등록 메커니즘(`register_subclass`)으로 연결되어
  **lerobot 소스 코드를 전혀 수정하지 않으며**, 업스트림 업그레이드 시 다시 sync만 하면 됩니다.
