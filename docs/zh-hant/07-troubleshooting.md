# 07 · 常見問題與經驗

本流程實際踩過的坑，依現象快速查閱。

## 環境類

| 現象 | 原因與解法 |
| --- | --- |
| `uv sync` 顯示 `failed to persist temporary file ... os error 17（跨盘）` | 本機 uv 快取目錄跨磁碟的 Windows 特例。所有 uv 指令前加上 `export UV_CACHE_DIR='C:\Users\admin\AppData\Local\Temp\uv-cache'` |
| 主控台刷出數十行 `libtorchcodec_core*.dll` 載入失敗 | 雜訊警告：torchcodec 載入失敗後會自動退回 **pyav**。實測（smoke [5]）pyav **編解碼影片資料集都正常**，狀態資料集和影片資料集都不受影響 |
| `python` 開啟 Microsoft Store | 使用 uv 管理的 Python；別用 Store 版 |

## 遙控操作類

| 現象 | 原因與解法 |
| --- | --- |
| 鍵盤控制「很慢」 | `--teleop.rate` 預設 60 單位/秒偏保守；提高到 **150** 手感正常（完整行程約 1.3s） |
| 啟動日誌刷出 `clamped to be safe` WARNING | 限速器追趕過程中的正常輸出，到位即停 |
| 主動臂居中時模擬臂偏幾度 | 校正範圍不對稱導致的固定偏移——使用 `so101_leader_trim` 自動微調（[05](05-leader-digital-twin.md)） |
| 連線瞬間手臂突然移動 | 這是設計行為：實機會上扭矩並朝中點/主動臂姿態移動；請保持手邊留有空間 |
| Ctrl-C 結束後手臂變軟下墜 | 正常：中斷時關閉扭矩，請用手扶一下 |
| 遙控操作/錄製期間打字會驅動手臂 | 鍵盤監聽**全域且不攔截按鍵**：任何視窗敲到對應按鍵（含拼音字母）都會進入按鍵佇列。鍵盤模式遙控操作/錄製時別打字；主動臂模式沒有此問題 |

## 錄製類

| 現象 | 原因與解法 |
| --- | --- |
| `q` 結束後，工作階段期間按的字母「一下子全吐在命令列」 | Windows 主控台輸入緩衝的積壓回顯；啟動器已內建 `drain_pending_keys()` 清理（只有舊工作階段才有此現象） |
| 某回合 action span 全為 0 | 空錄（人沒動）——錄前先動一下，或事後刪除該回合 |
| 回合開頭 1 秒誤差很大 | 收斂段：開始錄製瞬間從動臂還在初始位姿，主動臂已停在別處；事前將主動臂放到中位附近可避免 |
| `--dataset.root` 設成父目錄後資料集「不見了」 | **root 就是資料集目錄本身**；每場錄製換一個新的 root |
| `Esc` 和 `q` 的差異 | `q` 只停止錄製；`Esc` 還會中斷鍵盤遙控操作。兩者都能乾淨收尾（已修正），建議習慣使用 `q` |
| 儲存時 `ValueError: You must add one or several frames...` 行程帶著錯誤訊息結束 | 在回合**間隙**多按了 `→`/`n`（最常見：儲存 + 雙路影片編碼停頓數十秒、主控台看起來像卡住，手癢連按了幾次），旗標滯留到下一回合開頭被吃掉 → **0 影格空回合**，上游儲存空回合時崩潰（lerobot 已知邊界情況）。**已儲存回合不受影響、資料完好**；重新開啟工作階段續錄即可。**已加入防護**（2026-10-16）：`record.py` 在每個回合開始時清除間隙期間滯留的 `→`/`←` 旗標（錄製中按鍵照常生效），儲存前會列印 `saving the episode + encoding videos now...` 提示；回歸測試 `smoke_test.py` [7] |
| 開始錄製瞬間 `KeyError: 'wrist'`（含影像資料集） | 相機首個影格還沒渲染完成，就被錄製迴圈讀取了觀測；**已修正**（2026-10-16）：機器人外掛 `connect()` 現在會等到第一個影格就緒後才返回 |
| 含影片的指令碼顯示 `BrokenProcessPool` / `Invalid argument: '<stdin>'` | 影片編碼使用**多行程集區**，子行程需要依檔案路徑重新匯入入口模組——用 `python - <<EOF`（stdin）執行錄製指令碼就會崩潰。將指令碼存成真實的 `.py` 檔案再執行即可（真實入口 `record.py` 不受影響） |
| 儲存回合時 `SvtMalloc[fatal]: allocate memory failed ... av.error.MemoryError: [Errno 12] ... 'avcodec_open2(libsvtav1)'`，整個工作階段結束 | 上游預設編碼器 **libsvtav1** 在雙相機（wrist+top）兩路編碼同時開啟時，一次性大塊記憶體配置失敗（在模擬 + 預覽視窗佔用下更容易觸發；2026-10-16 實測遇過）。**已修正**：`record.py` 預設注入 `--dataset.rgb_encoder.vcodec=h264`（雙路 h264 同時編碼實測通過；明確傳入 vcodec 可覆寫）。已儲存回合無損；崩潰可能在資料集目錄留下 `tmp*/` 和孤立 parquet（依 run2 的方式清理） |
| 錄製中畫面變得卡頓（尤其按下 `→` 之後），但操作其實沒有延遲 | 卡住的是**儲存/編碼時段**：編碼行程預設吃滿 CPU（雙路影片同時編碼），同時模擬執行緒還在渲染 5 個畫面（內顯更明顯）。控制迴路本身不受影響——以 cadence 數字為準（實測全程 29.97Hz、0 tick 超出預算）。**已緩解**（2026-10-16）：`record.py` 預設 `--dataset.encoder_threads=2`（每路編碼限制 2 個執行緒）；相機預覽視窗更新頻率降至 15Hz（`--robot.preview_fps`）。回合越短，儲存時段佔比越大、感受越卡；想徹底消除停頓可使用 `--dataset.streaming_encoding=true`（邊錄邊編碼，上游推薦，待實測） |
| 儲存回合時編碼器顯示**記憶體配置失敗**、整場結束（svtav1 的 `SvtMalloc`、x264 的 `malloc ... failed`、`avcodec_open2` 報錯都屬此類） | 本機系統提交記憶體（commit）長期逼近上限（2026-10-16 實測 **105.9GB / 119.7GB**，已連續開機 29 天）。每次儲存都會新啟動 2 個編碼行程（各自載入 torch/av，commit 尖峰很大），在臨界邊緣同時啟動就會失敗。**已緩解**：`record.py` 現在為編碼加入**失敗自動重試一次**（暫時性失敗不再遺失回合），儲存期間日誌刷屏也已靜音（`av.logging.set_libav_level` + HF 進度條）。**根本解決 = 重新啟動電腦**（清理長時間執行累積的 commit / 核心記憶體洩漏；使用者模式行程只佔 27GB，其餘在核心/驅動層，無法終止）；自行檢查：`Get-Counter '\Memory\Committed Bytes'` vs `'\Memory\Commit Limit'` |

## 硬體類

| 現象 | 原因與解法 |
| --- | --- |
| COM 埠號和上次不一樣 | 序列埠號會隨插拔/更換連接埠而變化，每次先列出連接埠確認（[03](03-hardware-calibration.md)） |
| 唯讀檢查提示缺少伺服馬達 | 接線/供電問題；先檢查驅動板與線序，別急著校正 |
| `shoulder_lift` 方向與直覺相反（模擬） | 該模型的正方向朝下，映射前先驗證符號（[02](02-sim-model-verification.md)） |

## 設計說明（為什麼這樣做）

- **MuJoCo 會改寫網格頂點資料**：`<mesh>` 載入後，`mjModel.mesh_vert` 儲存的是**網格自身座標系**中的
  頂點（原點被重新定位到頂點重心、軸向被重新排列），不再是檔案原始座標——直接用它計算包圍盒/套用 CAD 尺寸會
  得到錯誤結果（渲染顯示不受影響）。若要取得 CAD 真實幾何，請用原始檔案解析（`preview_mount.py` /
  `step_to_stl.py` 的做法）。遇過一次：支架真實尺寸 54.3 × 35.0 × 75.0 mm。
- **MuJoCo 相機的取景方向是它座標系的 −Z**：`<camera>` 元素不朝自身 +Z（鏡頭凸起方向）看。第一版
  相機模組把鏡頭建在 +Z、元素朝向 identity → 畫面實際從 PCB 背面「反向看」出去，**鏡頭指向和畫面方向
  正好相反**（調參時「轉的方向和畫面對不上」的根源；2026-10-16 用紅/藍板對照渲染測試定位）。
  修正：相機元素繞 Y 旋轉 180°（`view.quat = RPY(0,180,0)`，preview_mount / adjust_camera / 機器人外掛
  三處統一）；`adjust_camera.py` 新增 "sim_cam live view" 即時畫面視窗，調整鏡頭所見即所得。
- **官方教學 MJCF 的夾爪是「鳥喙式」點接觸爪**：兩片齒尖閉合到 ~2.3 mm 點接觸、幾乎沒有可用的夾持面。
  系統物理實驗（2026-10-16，數百組）結論：方塊放在齒口附近任意位置，都會在 ~100° 的閉合掃掠中被
  鏟走/楔出，無法夾起（16–34 mm 方塊皆如此；機械行程與力矩本身正常）。**注意：不要用「補碰撞片」的
  方式修正**——曾試過給兩爪補齒板（能顯著改善夾持），但那是**實機上不存在的幾何**，訓練出的策略會
  依賴它、造成 sim2real 失真，已撤除。正確的修正方法是用**實機的爪部幾何替換官方模型的爪**（如
  mujoco_menagerie 的 SO-ARM101 或自家 CAD 重建），物理參數則應保持與實機一致。
- **官方預設接觸參數太「軟」，會造成物理穿透**：`solref` 時間常數預設 20 ms，快速/薄的接觸
  （方塊落到薄爪面上、閉合掃掠）會「還來不及產生力」就互相穿過——症狀就是「方塊直接穿過爪面掉下去」。
  修正（2026-10-16）：接觸參數硬化——`harden_mesh_contacts` 在編譯後將所有網格碰撞體的 `solref`
  硬化到與 menagerie 齒面相同（0.01 s），方塊接觸也同樣處理。純粹是物理保真度修正，不新增任何幾何。
- **模擬機器人已遷移至 mujoco_menagerie 的 SO-ARM100 模型**（2026-10-16）：原教學 zip 的 MJCF 是
  運動學展示品、爪無法夾取；menagerie 模型依實機 CAD 處理——爪部有專用碰撞齒面與硬接觸參數，
  四個齒位（淺→深）實測皆能頂停 + 夾住 + 提起 34mm 方塊。遷移要點：模型 vendored 於
  `assets/menagerie_so_arm100/`（Apache-2.0，含 LICENSE）；關節映射與單位符號見 `MODEL_JOINT`
  （逐關節對照舊模型的世界運動測定；wrist_roll 符號待實機遙控操作複核）；模型 Base 繞 Z 旋轉 +90° 使其
  工作正面朝 +x；支架改掛在 Fixed_Jaw（6 號伺服馬達）側面（先解析搜尋定位，2026-10-16 由使用者對照實機
  照片以 `adjust_mount.py --model menagerie` 手動微調定稿：`[0.1, -0.7, 24.7]mm`、`RPY [0.34, -27.20, 89.51]°`）。舊教學模型與工具保留未動，可隨時對照。
- **為什麼使用 uv 專案環境而不是 conda**：`.venv` 與專案同目錄、由 `uv.lock` 鎖定版本、刪除目錄即回收，
  和電腦上的 conda 環境完全隔離；`uv run` 從不往已啟用的 conda 裡安裝東西。本機的 `lerobot` conda 環境
  指向的是**另一個儲存庫副本**（`lerobot-main`），兩者互不干擾。
- **為什麼外掛都放在 `examples/so101_mujoco/`**：透過官方註冊機制接入（`register_subclass`），
  **零修改 lerobot 原始碼**；升級上游僅需重新 sync。
