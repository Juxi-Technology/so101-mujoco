# 07 · Problèmes fréquents et retours d'expérience

Les pièges réellement rencontrés dans ce parcours, à consulter rapidement par symptôme.

## Environnement

| Symptôme | Cause et solution |
| --- | --- |
| `uv sync` renvoie `failed to persist temporary file ... os error 17（跨盘）` | cas particulier Windows où le répertoire de cache uv de cette machine est sur un autre disque. Précédez toutes les commandes uv de `export UV_CACHE_DIR='C:\Users\admin\AppData\Local\Temp\uv-cache'` |
| La console affiche des dizaines de lignes d'échec de chargement de `libtorchcodec_core*.dll` | avertissement bruyant : après l'échec de chargement de torchcodec, repli automatique sur **pyav**. Testé (smoke [5]) : pyav **encode et décode normalement les jeux de données vidéo** ; ni les jeux de données d'état ni les jeux de données vidéo ne sont affectés |
| `python` ouvre le Microsoft Store | utilisez le Python géré par uv ; n'utilisez pas la version du Store |

## Téléopération

| Symptôme | Cause et solution |
| --- | --- |
| Le contrôle au clavier « très lent » | `--teleop.rate` vaut 60 unités/seconde par défaut, trop prudent ; passer à **150** donne une sensation normale (course complète en environ 1,3 s) |
| Les logs de démarrage affichent des WARNING `clamped to be safe` | sortie normale du limiteur de vitesse pendant le rattrapage ; elle s'arrête une fois la cible atteinte |
| Le bras simulé est décalé de quelques degrés quand le bras maître est centré | biais fixe dû à l'asymétrie de la plage de calibration — utilisez l'ajustement automatique `so101_leader_trim` ([05](05-leader-digital-twin.md)) |
| Le bras bouge soudainement à la connexion | comportement voulu : le robot réel applique le couple et se déplace vers le point médian/la pose du bras maître ; gardez de l'espace autour de vous |
| Après Ctrl-C, le bras devient mou et s'affaisse | normal : le couple est coupé à la déconnexion ; soutenez-le à la main |
| Taper au clavier pendant la téléopération/l'enregistrement pilote le bras | l'écoute du clavier est **globale et n'absorbe pas les touches** : toute frappe d'une touche mappée dans n'importe quelle fenêtre (y compris les lettres pinyin) entre dans la file de touches. Ne tapez pas pendant la téléopération/l'enregistrement en mode clavier ; le mode bras maître n'a pas ce problème |

## Enregistrement

| Symptôme | Cause et solution |
| --- | --- |
| Après avoir quitté avec `q`, les lettres tapées pendant la session « se déversent d'un coup dans la ligne de commande » | écho accumulé du tampon d'entrée de la console Windows ; le lanceur intègre désormais un nettoyage `drain_pending_keys()` (seules les anciennes sessions présentaient ce phénomène) |
| Un épisode a un action span entièrement à 0 | enregistrement vide (personne n'a bougé) — bougez d'abord avant d'enregistrer, ou supprimez l'épisode après coup |
| Une erreur importante pendant la première seconde de l'épisode | segment de convergence : au lancement, le bras esclave est encore dans sa pose initiale tandis que le bras maître est déjà ailleurs ; placez le bras maître près de la position médiane à l'avance pour l'éviter |
| Après avoir configuré `--dataset.root` sur un répertoire parent, le jeu de données « a disparu » | **root est le répertoire du jeu de données lui-même** ; changez de root à chaque session d'enregistrement |
| Différence entre `Esc` et `q` | `q` arrête seulement l'enregistrement ; `Esc` déconnecte aussi la téléopération au clavier. Les deux se terminent proprement (corrigé), mais prenez l'habitude d'utiliser `q` |
| À la sauvegarde, `ValueError: You must add one or several frames...` et le processus quitte avec l'erreur | appuis supplémentaires sur `→`/`n` pendant l'**intervalle** entre épisodes (cas le plus fréquent : la sauvegarde et l'encodage vidéo des deux flux prennent plusieurs dizaines de secondes, la console semble figée et on appuie plusieurs fois par impatience) ; le flag reste en attente et est consommé au début de l'épisode suivant → **épisode vide de 0 frame**, et la sauvegarde d'un épisode vide fait planter l'amont (limite connue de lerobot). **Les épisodes déjà enregistrés ne sont pas affectés et les données sont intactes** ; il suffit de rouvrir une session pour poursuivre l'enregistrement. **Protection ajoutée** (2026-10-16) : `record.py` efface au début de chaque épisode les flags `→`/`←` restés en attente pendant l'intervalle (les appuis pendant l'enregistrement fonctionnent normalement) ; avant la sauvegarde, il affiche le message `saving the episode + encoding videos now...` ; test de régression `smoke_test.py` [7] |
| `KeyError: 'wrist'` au lancement de l'enregistrement (jeux de données avec images) | la boucle d'enregistrement lisait l'observation avant que la première frame de la caméra ne soit rendue ; **corrigé** (2026-10-16) : la méthode `connect()` du plugin robot attend désormais que la première image soit prête avant de revenir |
| Un script avec vidéo renvoie `BrokenProcessPool` / `Invalid argument: '<stdin>'` | l'encodage vidéo passe par un **pool de processus** ; les processus enfants réimportent le module d'entrée à partir du chemin de fichier — exécuter le script d'enregistrement via `python - <<EOF` (stdin) provoque un crash. Enregistrez le script dans un vrai fichier `.py` et relancez-le (le point d'entrée réel `record.py` n'est pas affecté) |
| À la sauvegarde d'un épisode, `SvtMalloc[fatal]: allocate memory failed ... av.error.MemoryError: [Errno 12] ... 'avcodec_open2(libsvtav1)'` et toute la session se termine | l'encodeur amont par défaut **libsvtav1** échoue à allouer un gros bloc de mémoire d'un coup lorsque deux encodages (wrist+top) s'ouvrent simultanément (plus probable avec la simulation + les fenêtres d'aperçu ; rencontré en test le 2026-10-16). **Corrigé** : `record.py` injecte par défaut `--dataset.rgb_encoder.vcodec=h264` (encodage h264 double flux simultané validé en test ; un vcodec explicite le remplace). Les épisodes déjà sauvegardés sont intacts ; un crash peut laisser `tmp*/` et des parquet orphelins dans le répertoire du jeu de données (nettoyer comme pour run2) |
| L'image saccade pendant l'enregistrement (surtout après avoir appuyé sur `→`), mais les commandes ne sont pas réellement retardées | ce sont les **fenêtres de sauvegarde/encodage** qui saccadent : les processus d'encodage monopolisent le CPU par défaut (double flux vidéo simultané), tandis que le thread de simulation continue de rendre 5 vues (plus visible avec un GPU intégré). La boucle de contrôle elle-même n'est pas affectée — fiez-vous aux chiffres de cadence (29.97Hz et 0 tick hors budget sur toute la session). **Atténué** (2026-10-16) : `record.py` utilise par défaut `--dataset.encoder_threads=2` (2 threads par flux d'encodage) ; le rafraîchissement des fenêtres d'aperçu est réduit à 15 Hz (`--robot.preview_fps`). Plus les épisodes sont courts, plus la part de la fenêtre de sauvegarde est grande et plus la saccade se ressent ; pour supprimer complètement la pause, utilisez `--dataset.streaming_encoding=true` (encodage pendant l'enregistrement, recommandé en amont, à tester) |
| À la sauvegarde d'un épisode, l'encodeur signale un **échec d'allocation mémoire** et toute la session se termine (relèvent de cette catégorie : `SvtMalloc` de svtav1, `malloc ... failed` de x264, les erreurs `avcodec_open2`) | la mémoire commitée du système sur cette machine approche durablement de la limite (mesure du 2026-10-16 : **105.9GB / 119.7GB**, machine allumée en continu depuis 29 jours). Chaque sauvegarde démarre 2 nouveaux processus d'encodage (chacun charge torch/av, gros pic de commit) ; lancés simultanément au bord de la falaise, ils font tout basculer. **Atténué** : `record.py` ajoute désormais **un retry automatique en cas d'échec** d'encodage (un échec transitoire ne fait plus perdre l'épisode), et le bavardage des logs pendant la sauvegarde est mis en sourdine (`av.logging.set_libav_level` + barre de progression HF). **Remède définitif = redémarrer la machine** (éliminer le commit accumulé / les fuites du noyau ; les processus utilisateur n'occupent que 27GB, le reste est dans le noyau/les pilotes, impossible à tuer) ; pour vérifier soi-même : `Get-Counter '\Memory\Committed Bytes'` vs `'\Memory\Commit Limit'` |

## Matériel

| Symptôme | Cause et solution |
| --- | --- |
| Le numéro de port COM diffère de la dernière fois | le numéro de port série change à chaque branchement/changement de port ; listez les ports avant chaque connexion pour vérifier ([03](03-hardware-calibration.md)) |
| Le contrôle en lecture seule signale un servomoteur manquant | problème de câblage/alimentation ; vérifiez d'abord la carte driver et l'ordre des fils, ne vous précipitez pas sur la calibration |
| La direction de `shoulder_lift` est contre-intuitive (simulation) | dans ce modèle, le sens positif pointe vers le bas ; vérifiez le signe avant le mapping ([02](02-sim-model-verification.md)) |

## Notes de conception (pourquoi ces choix)

- **MuJoCo réécrit les données de sommets des maillages** : après chargement d'un `<mesh>`, `mjModel.mesh_vert` contient les sommets dans le **repère propre du maillage** (origine recentrée sur le barycentre des sommets, axes réordonnés), et non plus les coordonnées d'origine du fichier — l'utiliser directement pour calculer une boîte englobante ou reporter des dimensions CAO donne des résultats erronés (l'affichage du rendu n'est pas affecté). Pour obtenir la géométrie CAO réelle, analysez le fichier d'origine (approche utilisée dans `preview_mount.py` / `step_to_stl.py`). Rencontré une fois : dimensions réelles du support 54.3 × 35.0 × 75.0 mm.
- **La direction de visée d'une caméra MuJoCo est le −Z de son repère** : l'élément `<camera>` ne regarde pas vers son propre +Z (la direction de protrusion de l'objectif). La première version du module caméra plaçait l'objectif en +Z avec une orientation d'élément identity → l'image était en fait prise « à l'envers » depuis l'arrière du PCB, **la direction de l'objectif et celle de l'image étant exactement opposées** (racine du « le sens de rotation ne correspond pas à l'image » lors du réglage ; localisé le 2026-10-16 par un test de rendu comparatif avec des plaques rouges/bleues).
  Correction : l'élément caméra tourne de 180° autour de Y (`view.quat = RPY(0,180,0)`, appliqué de façon uniforme dans preview_mount / adjust_camera / le plugin robot) ; `adjust_camera.py` ajoute une fenêtre d'image en temps réel « sim_cam live view », pour régler l'objectif avec un retour immédiat.
- **La pince du MJCF du tutoriel officiel est une pince à contact ponctuel « en bec d'oiseau »** : les deux pointes de dents se ferment en contact ponctuel à ~2.3 mm, avec quasiment aucune surface de préhension utilisable.
  Conclusion des expériences physiques systématiques (2026-10-16, plusieurs centaines de configurations) : un cube placé n'importe où près de l'ouverture des dents est poussé/éjecté lors du balayage de fermeture d'environ 100°, impossible à saisir (même comportement pour des cubes de 16–34 mm ; la course mécanique et le couple sont eux-mêmes normaux). **Attention : ne corrigez pas en « ajoutant des plaques de collision »** — l'ajout de plaques dentées aux deux mors a été essayé (amélioration nette de la préhension), mais c'est une **géométrie inexistante sur le robot réel** ; une politique entraînée s'appuierait dessus et provoquerait une distorsion sim2real, donc retiré. La bonne correction est de **remplacer la pince du modèle officiel par la géométrie de pince du robot réel** (par exemple le SO-ARM101 de mujoco_menagerie ou une reconstruction CAO maison), en conservant des paramètres physiques cohérents avec le robot réel.
- **Les paramètres de contact par défaut officiels sont trop « mous » et provoquent des traversées physiques** : la constante de temps `solref` vaut 20 ms par défaut ; les contacts rapides/fins (cube tombant sur une face de mors fine, balayage de fermeture) se traversent mutuellement « avant d'avoir eu le temps de générer une force » — symptôme : « le cube traverse directement la face du mors et tombe ».
  Correction (2026-10-16) : durcissement des paramètres de contact — `harden_mesh_contacts` durcit après compilation le `solref` de tous les corps à collision maillés à la valeur utilisée par les faces dentées de menagerie (0.01 s), et traite de même le contact des cubes. Correction pure de fidélité physique, sans ajout de géométrie.
- **Le robot simulé a migré vers le modèle SO-ARM100 de mujoco_menagerie** (2026-10-16) : le MJCF du zip du tutoriel d'origine est une démonstration cinématique dont la pince ne peut pas saisir ; le modèle menagerie suit la CAO du robot réel — la pince dispose de faces dentées de collision dédiées et de paramètres de contact durs, et les quatre positions de dents (peu profond→profond) permettent toutes, en test, de bloquer, saisir et soulever un cube de 34 mm. Points clés de la migration : le modèle est intégré (vendored) dans `assets/menagerie_so_arm100/` (Apache-2.0, LICENSE incluse) ; le mapping des articulations et les signes d'unités se trouvent dans `MODEL_JOINT` (déterminé articulation par articulation par mesure du mouvement dans le monde par rapport à l'ancien modèle ; le signe de wrist_roll reste à revérifier par téléopération sur le robot réel) ; la Base du modèle tourne de +90° autour de Z pour orienter sa face de travail vers +x ; le support est désormais fixé sur le flanc de Fixed_Jaw (servomoteur n° 6) (localisé d'abord par recherche analytique, puis réglé manuellement le 2026-10-16 par l'utilisateur en comparant avec des photos du robot réel via `adjust_mount.py --model menagerie` : `[0.1, -0.7, 24.7]mm`, `RPY [0.34, -27.20, 89.51]°`). Les anciens modèles et outils du tutoriel sont conservés intacts pour comparaison à tout moment.
- **Pourquoi utiliser l'environnement de projet uv plutôt que conda** : `.venv` se trouve dans le même répertoire que le projet, les versions sont verrouillées par `uv.lock`, et supprimer le répertoire suffit à tout récupérer ; il est totalement isolé des environnements conda de la machine ; `uv run` n'installe jamais rien dans le conda activé. L'environnement conda `lerobot` de cette machine pointe vers **une autre copie du dépôt** (`lerobot-main`) ; les deux ne s'interfèrent pas.
- **Pourquoi tous les plugins sont dans `examples/so101_mujoco/`** : ils s'intègrent via le mécanisme d'enregistrement officiel (`register_subclass`), **sans aucune modification du code source de lerobot** ; une mise à jour de l'amont ne demande qu'un nouveau sync.
